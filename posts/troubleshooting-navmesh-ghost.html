编辑器里正常、运行时抽风，先怀疑磁盘上的烘焙数据。

前言 ​

最近在写 UE 的时候，碰上了一个相当灵异的问题。

从主菜单切进主地图之后，导航网格上居然出现了早就删掉的几何体——绿色的可行走区域里，明晃晃地躺着几个迭代之前就已经删掉的斜坡。敌人按照这个「鬼影」巡逻，范围自然就全乱了。

我手动挪一下 NavMeshBoundsVolume，强制它重建一遍，绿区立刻恢复正常；但只要下次切图，鬼影又回来了。而且编辑器视口和直接打开地图 PIE 都完全正常，只有走主菜单切图这条路才会出事。

这种「一半正常一半不正常」的 bug 最折磨人，因为你很难第一时间判断是自己的代码问题、引擎问题，还是玄学。

现象描述 ​

先把症状梳理清楚，后面排查全靠这个当参照：

  1. 触发路径：主菜单 → 新游戏 → 切进主地图（OpenLevel）
  2. 异常表现：导航网格渲染出已删除几何体的可行走区域，敌人巡逻范围异常
  3. 临时缓解：挪动 NavMeshBoundsVolume 触发重建后恢复正常
  4. 复发规律：下次切图必定复发
  5. 对照组：编辑器视口正常、直接打开地图 PIE 也正常

注意第 5 条，这是整个排查过程中最有价值的线索——同一张地图，有的打开方式正常，有的不正常。有差异，就意味着有突破口。

排查过程 ​

一开始把能想到的方向都试了一遍。这里把整个「弯路」完整记录下来，因为每一条失败的尝试其实都在缩小问题范围。

尝试结果结论
DefaultEngine.ini 设 RuntimeGeneration=Dynamic无效不是运行时生成时机的问题
设 ForceRebuildOnLoad=True无效属性名写错了（见后文经验 3）；而且就算重建成功，也救不了磁盘上的旧数据
搜关卡演员文件，找残留斜坡没有任何引用几何体确实已删除，不是藏起来的演员
找烘焙出来的独立导航数据文件没有独立导航资产旧数据藏在地图资产内部
动 bounds → Ctrl+S → 重开编辑器鬼影复现「重建 + 保存」并没有真正把新数据写回磁盘
差分实验：直接 PIE vs 主菜单切图直接进正常，切图有鬼影锁定：只有走磁盘加载的路径才会读到旧数据

前面几条全是无效功，但每一条都排除了一个假设。真正破局的是最后那个差分实验：固定所有其他变量，只换「进入地图的方式」这一个条件。结果一次实验就把问题域二分出来了——内存里的数据是干净的，磁盘上的数据是脏的。

根因分析 ​

结论先行：地图资产内部烘焙着一份过期的导航网格数据，而「切图」这条路径恰好读的是这份磁盘数据。

UE 的导航网格实际上有两条数据来源，分别对应两种完全不同的加载路径：

编辑器内存路径 ​

在编辑器里打开地图时，编辑器会基于当前关卡里的几何体自动重建一份干净的导航网格，存放在内存中。编辑器视口渲染的、以及「直接打开地图按 PIE」时使用（编辑器把当前内存数据交给 PIE 进程）的，都是这份数据。

所以只要你在编辑器里看，导航网格永远是对的——它根本不走磁盘。

磁盘烘焙数据路径 ​

但有两种情况不走内存，而是从磁盘加载地图资产里预先烘焙好的导航数据：

  • PIE 中途通过 OpenLevel 切图：此时目标关卡是作为资产从磁盘重新加载的，随资产一起读入的还有它内部烘焙的导航数据；
  • 打包后的运行时：不存在「编辑器内存重建」这一说，一切以资产文件为准。

问题就出在这两条路径的交汇点上：几何体改动之后，编辑器的自动重建 + 随手一个 Ctrl+S，并不总能保证导航数据完整地写回地图资产。于是磁盘上的那份烘焙数据一直停留在「旧几何体时代」，平时藏在编辑器内存背后看不出来，一旦走磁盘加载路径就原形毕露。

这也完美解释了前面的所有现象：

  • 编辑器视口正常 → 走内存路径，数据是新的；
  • 直接打开地图 PIE 正常 → 同上；
  • 主菜单切图有鬼影 → 走磁盘路径，读到的是过期烘焙数据；
  • 挪动 bounds 能临时修复 → 触发了内存重建，但没解决磁盘数据，所以必然复发。

解决方案 ​

找到根因之后，修复反而很简单，核心思路就一句话：强制把磁盘上的烘焙数据重新生成一遍，并确保真正写盘。

  1. 打开 FirstPersonMap；
  2. 菜单 Build → Build All Levels——强制重建全部烘焙数据，包括导航网格；
  3. File → Save All——注意是 Save All 而不是 Save Current，因为烘焙数据可能分散在多个包里，只存当前关卡可能漏掉一部分；
  4. 验证：主菜单 → 新游戏 → 切进地图，确认绿区与当前几何体完全一致。

到这里，鬼影彻底消失，切图也不再复发。

经验总结 ​

最后把这次排查沉淀下来的东西整理一下，以后再碰到类似的问题可以直接按这个思路走。

1. 「编辑器里正常，运行时异常」先怀疑磁盘烘焙数据 ​

编辑器内存里的数据和磁盘资产里的数据是两份独立的东西，它们完全可能不同步。任何「看的时候没事、跑起来出事」的问题，都应该先想到这个方向。

2. 差分实验是最快的定位手段 ​

固定其他所有变量，只切换一条路径（直接进 vs 切图进），一次实验就能把问题域二分出来。比漫无目的地改配置、猜原因高效得多。

3. ini 属性名必须精确 ​

UE 的布尔属性通常带 b 前缀，比如正确的写法是 bForceRebuildOnLoad，写成 ForceRebuildOnLoad 会被静默忽略，连个报错都没有。改完配置后，最好到 Project Settings 的 UI 里确认一下值是不是真的变了。

4. 看到「鬼影几何」先问数据来源 ​

先搞清楚它到底是哪来的：是当前关卡里的演员（去搜关卡数据确认），还是某个烘焙资产里的快照？来源不同，解法完全不同。

5. 大改几何体后养成习惯 ​

改完几何体顺手来一发 Build → Build All Levels + Save All。尤其是 World Partition 地图——导航是按区块（Cell）烘焙的，更容易残留过期数据。

6. 导航网格问题速查顺序 ​

以后再碰到绿区异常，按这个顺序排查，基本能覆盖绝大多数情况：

  1. 搜有没有残留 / 隐藏的演员；
  2. 差分「直接进」和「切图进」，判断是不是磁盘数据问题；
  3. Build All Levels + Save All；
  4. 删掉关卡里的 RecastNavMesh 对象，让它全新重建。

写在最后 ​

这个 bug 本身不算复杂，但它把「编辑器内存数据」和「磁盘烘焙数据」这两条容易被忽略的路径摆到了台面上。UE 里很多「灵异现象」其实都是类似的套路：你以为只有一份数据，实际上有好几份副本，而它们不同步。

遇到这种情况别慌，先做差分实验，再顺着数据流问一句：「你现在读的到底是哪一份？」——答案往往就藏在这里。
